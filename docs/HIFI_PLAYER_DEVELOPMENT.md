## 1. 目标与完成标准

Lazer 的目标是成为一个跨平台、对音频链路诚实且易用的播放器：用户能管理音乐、稳定地播放整张专辑、选择 USB DAC 或网络播放设备，并准确看到文件格式、实际输出格式和音频处理中每一步发生了什么。和 foobar2000 看齐的重点是**格式与设备可控、播放稳定、队列与媒体库可靠、状态可验证**，不是仅在设置页堆格式名称。

> 2026-10-05 桌面输出恢复集成回归：新增 JVM 测试以假 JNA 音频库驱动真实 `DesktopPlayerController`/`DesktopNativeAudioPlayer` 链路，覆盖 `DEVICE_LOST` 后短暂找不到端点、按同一稳定身份重枚举并重开、从事件位置恢复播放，以及恢复枚举期间 seek 取消迟到重开；同一检查点再次丢失也确认不会进入无界重试。定向 `DesktopPlayerControllerNativeRecoveryTest` 通过。它验证控制器到 native API 的软件闭环，仍不代表实体 USB DAC 拔插、独占占用或硬件恢复已验证。

### 先用这几条判断功能是否真的可用

- **能解码，不等于能按原格式输出。** 播放器读得懂 DSD 文件，只说明它能解码；如果随后转换成 PCM 播放，应显示“DSD→PCM”，不能称为 Native DSD。
- **设备报告，不等于 DAC 已确认。** 播放器可以询问操作系统支持哪些格式，也可以报告已建立的输出会话格式；这仍不能证明 DAC 收到的物理格式，更不能单独证明样本逐位一致。
- **bit-perfect 是受限的播放模式。** 对无损 PCM 来说，采样、声道和样本值必须原样送出。数字音量、EQ、ReplayGain、限幅、重采样或系统混音都会改变信号，因此要么旁路这些处理，要么明确说明当前不是 bit-perfect。
- **“好用”与“高规格”同样重要。** 自动匹配 DAC 格式、整张专辑稳定播放、设备拔插后给出明确状态，以及让用户看懂发生了什么，优先于列出尚未实测的最高采样率或 DSD 倍率。

这份方案按“文件能否读取 → 平台能否建立输出 → 设备是否按预期工作 → 数字回采是否逐样本一致”逐层验收。每一层的证据都单独记录，避免把某一层的成功误当成整条链路已通过。

第一阶段只承诺已实测的设备、格式和平台组合。产品文案中的“bit-perfect”必须有可重复的数字验证；“支持 768 kHz / DSD1024”只能表示**在设备、驱动、平台和接口都报告支持且测试通过时**可用，不能表示所有平台和所有 DAC 都能输出。

成功标准：

1. 44.1/48/96/192 kHz PCM 专辑在目标 DAC 上自动切换物理采样率，跨曲目不中断、不误报；高于 192 kHz 的支持按设备矩阵逐项扩展。
2. 设备可用且选择直通时，输出采样与源 PCM 逐帧一致；不满足条件时清楚显示转换原因，不冒称 bit-perfect。
3. 可在播放中处理设备拔插、独占占用、网络中断和系统音频焦点变化；不会突然全音量或无声卡死。
4. 同一张专辑可无缝播放；音量、EQ、ReplayGain、交叉淡化等处理是否生效，在信号路径中可见。
5. 每个平台有自动化信号测试及真实 DAC 回环或采集测试，发布页只展示通过的能力矩阵。

2026-10-03 桌面 native 播放链路已接入单后继曲目的 gapless 队列：预备的兼容音源沿用当前已打开的输出会话，连续 PCM 追加到同一 ring，输出帧边界触发 `TrackChanged`，桌面控制器据此切换曲目状态并准备下一首。为保留采样率自动协商，后继曲目的源采样率必须匹配当前曲目；跨采样率曲目会走逐曲停止/重开，以便设备重新协商。队列编辑、播放模式变化、停止和显式切歌会使旧请求代次失效；bit-perfect 还会拒绝不匹配的 PCM 位深/声道格式，并走逐曲回退。Native Engine 的 fake-output 矩阵现对 PCM16/24/32 和 44.1–768 kHz 十档逐字节比对 A、B 样本连续拼接；每个组合只打开/启动/关闭一次输出，另覆盖队列撤销后的代次失效。边界快照回归会暂停 fake output 消费，在解码器已切到 B、但 A 尚未播完时确认 snapshot 与 stream info 仍描述 A；输出越过接缝后回调内重入查询会看到 B。native `seek` 的目标是当前已由解码器激活的 source：B 尚未激活时作用于 A；B 已激活但 A 的输出帧尚未播完时作用于 B。后一情况下，seek 会清除旧输出并以 B 的 seek 位置重新填充；A 的旧接缝不会提前发布，`TrackChanged` 会在 B 的 seek 后输出帧实际被消费后发布一次。若 B 已被完整预解码，seek 会重启其有界预解码队列；引擎 pump 会等到待发布的输出帧边界提交后再结束。桌面 UI 的 seek 仍按控制器当前曲目重开音源，不调用这个 native seek API。上述证据只证明软件引擎在合成 WAV 与 fake output 下的连续 PCM、格式打包及边界/seek 展示状态；不验证 WASAPI/ALSA 实机格式、DAC 数字回采、HTTP 预取及时性、所有解码器组合或超短曲目，不能据此标注所有平台均已支持 gapless。

## 3. 音频链路的硬规则

### 3.1 格式与直通定义

将链路建模为：`音源 → 解封装/解码 → 可选 DSP → 格式适配 → 平台输出 → 驱动/传输 → DAC`。分别记录**源格式、解码后格式、交给平台的格式、平台报告的设备格式**；不能只显示文件标称的“24/192”。

PCM 直通成立条件：源是无损 PCM 表示；解码后的样本值、通道映射、采样率与输出有效位精确匹配；不发生 SRC、数字音量、EQ、限幅、ReplayGain、交叉淡化或系统混音；输出后端提供可验证的专用/直通路径。位深容器（如 24 位有效数据装在 32 位容器）与有效位数要分开记录。无损解码后的 PCM 可以做样本级直通验证；有损 MP3/AAC 解码输出不叫“原始文件 bit-perfect”。

直通协商必须按顺序：查询目标设备能力 → 首选源采样率/有效位深/通道 → 调用 `IAudioClient::Initialize` 并记录实际传入且成功初始化的会话格式 → 若它与解码样本完全匹配则满足 WASAPI 格式条件 → 若不匹配，按用户策略“停止并提示”或“允许转换”执行。`IsFormatSupported` 只是 `Initialize` 前的候选查询，不替代成功初始化；WASAPI 会话格式也不是 DAC 的物理输出回读。设备不接受原格式时，不能静默回落还继续亮“直通”。播放前切换采样率，停止/切换设备时释放独占和相关资源。播放器不可全局固定 48 kHz。[Microsoft stream management](https://learn.microsoft.com/en-us/windows/win32/coreaudio/stream-management)

### 3.2 音量、EQ 与 Dither

- 音量模式为“设备硬件音量 / 软件音量 / 固定电平”。默认先探测硬件音量是否真实存在；没有硬件控制时，不把系统软件 endpoint 音量冒充硬件音量。首次进入固定电平或直通前给出一次明确的音量提示，并保留可恢复的安全设置。
- USB Audio Class Feature Unit 的控制须按设备描述符与平台权限实现；`SET_CUR` 不是跨平台应用层统一接口。Windows 已只读查询 `IAudioEndpointVolume::QueryHardwareSupport`，flags 仅说明 Windows endpoint 报告的硬件音量、静音或电平表能力，不证明 USB UAC Feature Unit 可访问。[Microsoft QueryHardwareSupport](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nf-endpointvolume-iaudioendpointvolume-queryhardwaresupport)
- `IAudioEndpointVolume` 控制的是端点主音量，Microsoft 提醒修改它可能影响其他音频应用；查询到硬件标志也不代表它是应用独占控制。Android 已有基于 USB Audio Class 1/2 Feature Unit 的独立诊断 SET_CUR/GET_CUR 控件，会核对描述符拓扑、权限、范围与回读；尚无 DAC 实机写入/恢复验证，也未证明所选 USB 设备等于当前 AudioTrack 输出路由。Windows 当前使用 IAudioEndpointVolume 端点主音量 API，仅在硬件支持标志存在时开放；两者都不代表跨平台统一的播放器硬件音量抽象。直通时桌面软件数字音量仍被锁定；用户也可使用 DAC 自身旋钮/遥控器。[Microsoft IAudioEndpointVolume](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nn-endpointvolume-iaudioendpointvolume)
- EQ 必须有一个显眼的“一键旁路”。EQ 开启后使用内部浮点处理、保留前级余量并监控削波；最后要缩减到整数 PCM 目标位深时加入正确的 dither。若目标仍为浮点或没有缩减位深，不应机械地加 dither。限幅器、ReplayGain 和软件音量都视为 DSP，开启即退出直通。
- 当前 native limiter 是样本峰值 ceiling：attack 即时生效，release 平滑；它不估算重建波形的 inter-sample true peak。ABI v8 已把 DSP 浮点路径的样本峰值、播放以来最大限幅衰减及整数输出量化时被饱和的样本数送到桌面 UI；浮点输出不显示整数削波计数，bit-perfect 路径不报告遥测。峰值和衰减是播放以来的保持值，计数是量化器输入超出 [-1, 1] 后被钳位的累计样本数。这些数据不代表 DAC 端削波、模拟输出峰值或 true peak。
- 当前 native bit-perfect PCM 模式旁路数字音量和 EQ；已有的 DSD/DoP 直通路径也不允许这些 DSP。项目目前没有 MQA 信号识别、MQA 专属透传开关或 DAC 确认，不把通用 FLAC bit-perfect 模式称为 MQA 透传。未来若取得正式 MQA 接口与许可，再按可验证的识别结果决定是否暴露 MQA 状态。

### 3.3 切歌与错误恢复

预解析下一首、维持缓存和设备连接，只有下一曲格式确实变化才重新协商设备。不能以交叉淡化伪装无缝播放；原生 gapless 在连续 PCM 帧边界不得插入静音。对设备丢失、独占被拒、无权限、采样率不支持、网络断流分别给出可执行的错误提示和可配置回退策略。音频回调线程不得等待网络、磁盘或 UI 锁。

## 4. 格式路线

| 能力 | 实施要求 | 对外承诺条件 |
| --- | --- | --- |
| PCM 16/24/32 bit，44.1–768 kHz | 解码与播放分层；输出后端枚举设备所接受的整数/浮点格式；区分有效位与容器位；44.1 kHz 与 48 kHz 家族都要测 | 每个采样率/位深仅在对应设备与平台实测通过后列入矩阵 |
| DSD64–1024 文件读取 | Windows 原生路径保留 raw DSD 帧；DSF 与未压缩 DFF mono/stereo 支持 DSD64–1024，raw DFF 限 DSDIFF 1.5.0.0；DST DFF mono/stereo 经 FFmpeg decoder→float PCM。五档倍率合成 verbatim-frame 夹具均通过 44.1 kHz PCM 解码/EOF；一份真实 DSD64 stereo FATE profile 通过 44.1/96 kHz decode/seek/EOF。含 DSTC、多声道和其他压缩 profile 尚未支持或验证 | “可读取”与“原生输出”分别声明；DST 仅可标为 DSD→PCM |
| DoP | 保持 DSD 位流，按 DoP 帧封装，DAC 支持时才发送；禁止 SRC、音量和 DSP | 设备端识别 DoP 且回采样验证通过。DoP 的 PCM 载波速率随 DSD 倍率上升，DSD512/1024 可能超过常见 PCM 768 kHz 输出上限，不能一概承诺 |
| Native DSD | Linux ALSA `hw:` 已实现 raw DSD 到精确 DSD_U8/U16/U32 格式协商与字组输出；其余平台尚未实现 | Linux 需先通过 Actions 构建、ALSA loopback 与实体 DAC 识别验证；Windows 后续评估 ASIO/厂商接口，其他平台逐设备研究；不能把普通 UAC2 PCM 输出称为 Native DSD |
| DSD→PCM | Windows 原生 raw DSD 帧经 FFmpeg libswresample 转 float PCM；输出采样率由 WASAPI 协商。UI 显示 DSD 倍率和 PCM 会话格式。合成源 seek/EOF 已过指定范围，真实源、多声道、高倍速 CPU/设备测试仍待做 | 能播放但标记为转换路径，绝不显示 DSD bit-perfect |
| MQA | **未实现。** 当前没有 MQA 信号/元数据识别、专属透传开关、软件解码或 DAC 能力/确认接口。通用 FLAC bit-perfect 仅表示满足精确 PCM 条件时保留解码样本，不表示已识别 MQA 或 DAC 正在 MQA 解码 | 不按文件扩展名、位深、采样率、标签或 DAC 型号猜测 MQA。取得 Lenbrook Media Group 对技术接口、解码/商标许可与认证的书面说明，并有兼容 DAC 验证后再立项；未确认前不宣传 MQA 支持 |

桌面 DoP 软件路径已按以下帧契约实现，目前仅接受 raw mono/stereo DSD：FFmpeg `AV_SAMPLE_FMT_DSD` 是 MSB-first 的交错位流，每个输入 sample 为每声道一个 DSD 字节。每个 DoP 载波帧每声道消费两个连续 DSD 字节，组成一个 24-bit word；little-endian packed PCM 的内存字节顺序是 `[DSD byte 0, DSD byte 1, marker]`，marker 位于有效样本最高 8 位并在每个载波帧间交替 `0x05`/`0xFA`。载波率为 DSD bit rate / 16，即 DSD64/128/256/512/1024 对应 176.4/352.8/705.6/1411.2/2822.4 kHz；设备必须精确接受该载波率与 24-bit 有效格式，不能做 SRC 或 DSP。DST DFF 经 FFmpeg 转为 float PCM 后不再有可封装的原始 DSD 位流，应明确走 PCM 转换或拒绝 DoP。后端成功打开载波 PCM 只表示 PCM 会话初始化成功，不证明 DAC 识别了 DoP。[DoP Open Standard 1.1](https://dsd-guide.com/sites/default/files/white-papers/DoP_openStandard_1v1.pdf)、[FFmpeg sample formats](https://ffmpeg.org/doxygen/trunk/group__lavu__sampfmts.html)

`lazer-audio-dop-packer` 验证字节序、声道分离、marker 交替、奇数分块连续性、EOF 尾字节补齐、变量周期 marker 连续性及容量不足重试；`lazer-audio-source-probe --dop` 已通过 Windows DSD64 source/seek 后缀比对。DoP 已连入桌面 native Engine、WASAPI/ALSA exact-format adapter 与 UI；Engine fake-output 回归检查 PCM 不受全局 DoP 偏好影响、raw stereo DSD 的精确载波格式协商、payload 声道分离、跨 writable-frame grant 的 marker 连续性，以及同倍率/字节时钟/声道的 raw DSD 后继能否在同一载波会话 gapless 播放。gapless 用例断言单次打开、两首曲目的 payload 顺序、奇数 carrier 边界后的 marker 连续和单次 `TrackChanged`；不兼容倍率会被拒绝预载并在正常曲目切换时重开载波。Linux/ALSA probe 尚未编译运行，也没有实体 DAC 对 marker 锁定或数字回采记录。DoP 模式强制独占并旁路 DSP/数字音量；仅对 raw mono/stereo DSD 生效，PCM 和不支持封装的 DSD 继续按 PCM 输出；播放器尚不声称 DAC 已识别 DoP。

DSD 速率、DoP 载波和 DAC 支持需逐项确认。Lenbrook 将 MQA 商业化交由 Lenbrook Media Group 负责；因此在开发 MQA 专属识别、软件解码或品牌功能前，应向其获取当前接口与书面许可说明，不根据旧 SDK、旧许可或设备宣传推断当前集成权利。[Lenbrook 收购公告](https://lenbrook.com/lenbrook-extends-leadership-in-hi-res-audio-with-mqa-acquisition/)、[Lenbrook Media Group 商业化说明](https://lenbrook.com/lenbrook-spins-out-its-content-delivery-business/)。不要通过逆向工程绕开授权。

## 5. 平台输出后端

native 层已把本地 PCM 端点抽成内部 `AudioOutput`：设备能力属于 `OutputCapabilities`，成功打开后的协商结果属于 `AudioOutputSession`，两者不可混用。当前有 WASAPI、ALSA `hw:` 和 CoreAudio HAL 三个输出 adapter；FFmpeg/解码器和平台输出仍通过内部 PCM 帧队列连接。ABI v11 新增 UTF-8 ALSA 硬件播放 PCM 快照，桌面选择器按当前 OS 枚举 WASAPI、ALSA 或 CoreAudio 设备，并按稳定身份恢复用户选择；缺失的已保存设备保持不可用，不会静默切换到另一台设备。Windows endpoint 目录/音量/格式探测仍是独立的平台 API。CoreAudio 输出已在 macOS Apple SDK CI 中完成编译、CTest 与 JNA catalog 冒烟；设备行为和 DAC 验证仍待 macOS 主机。

Linux 构建/加载垂直切片已接入代码：CMake 选择 ALSA 输出并从 pkg-config 查找 FFmpeg/ALSA；FFmpeg 默认走系统 pkg-config，也可指定含四个 `.pc` 模块的自带开发包 root；文件新增 UTF-8 C ABI 入口；Gradle 能按 OS/架构选择 `.so`，并把构建目录中的原生库暂存到应用资源；JNA loader 已支持 Linux 资源路径。ABI v11 增加直接 ALSA 硬件 PCM 目录，桌面选择器显示播放 PCM 名称并保存 ALSA card ID 与 PCM 编号；card ID 不可用时身份标记为临时。ALSA `hw:` 没有通用系统默认映射，因此未选择设备时仍使用当前占位值 `hw:0,0`，设置中会直接显示该值。

Linux CI 已配置原生编译、DSD/DSP 离线探针、JNA 目录 API 冒烟，以及 ALSA 输出会话探针。只有同时显式设置 `LAZER_AUDIO_BUILD_PROBE=ON` 和 `LAZER_AUDIO_TEST_ALLOW_ALSA_NULL=ON` 的 Linux 测试构建，输出后端才接受 ALSA `null` PCM；该设备不进入目录。Gradle 原生分发构建显式关闭这两个选项，即使与 CI 共用 CMake 缓存也不会把测试路由带入发布库。探针检查 16/24/32 bit 格式协商、写入、暂停/恢复、重置和排空。它验证 ALSA 后端的软件状态与队列控制，不验证实体驱动、硬件时钟、XRUN 恢复或 DAC 端 bit-perfect。Linux CI 已完成原生编译、14 项 CTest、包含 ALSA null PCM 的输出探针与 JNA/ALSA 目录冒烟；snd-aloop、硬件驱动与 DAC 仍待 Linux 主机验证。[ALSA null PCM](https://www.alsa-project.org/alsa-doc/alsa-lib/pcm_plugins.html)

当前工作流在非 tag 构建中给 DEB/RPM、AppImage 和 runnable JAR 打入可选 `.so`，并检查归档内容；这些仅是 HiFi 候选构建。版本 tag 发布仍不传 `-PlazerNativeAudio=true`，所以正式 Linux 包暂不带这份原生引擎。启用时，Gradle 会给 DEB 声明 `libasound2 | libasound2t64`，给 RPM 声明 `alsa-lib`；它们只覆盖 ALSA 运行库。FFmpeg 动态库会与引擎一起复制，但其传递依赖仍需验证。JDK 21 的默认 DEB bundler 可借助 `ldd` 探测包内动态库并映射到构建主机的软件包；Ubuntu 上生成的 RPM 不是默认 bundler，依赖探测会关闭，RPM 模板也关闭了自动 Requires。AppImage 当前没有传递 ELF 依赖收集步骤。因而 DEB 需验证真实 `Depends` 与干净环境安装，RPM 需在 Fedora/RHEL 构建并验证 `Requires`，AppImage 需明确 FFmpeg/ALSA 传递依赖的打包策略；完成这些检查前不把原生引擎加入 tag 发布。[JDK 21 jpackage 依赖选项](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jpackage.html)、[JDK 21 Linux package bundler](https://github.com/openjdk/jdk21u/blob/master/src/jdk.jpackage/linux/classes/jdk/jpackage/internal/LinuxPackageBundler.java)、[动态库依赖探测](https://github.com/openjdk/jdk21u/blob/master/src/jdk.jpackage/linux/classes/jdk/jpackage/internal/LibProvidersLookup.java)、[RPM 模板](https://github.com/openjdk/jdk21u/blob/master/src/jdk.jpackage/linux/classes/jdk/jpackage/internal/resources/template.spec)。后续在 `snd-aloop` 或实体设备上验证真实 `hw:` 输出队列/恢复，再连接实体 DAC。不得把 WASAPI endpoint volume、`IsFormatSupported` 或 Windows endpoint ID 暴露为 ALSA 能力。ALSA `hw` 只表示直接 ALSA PCM 路径，格式协商成功仍不等于 DAC 物理格式回读或数字 bit-perfect 验证。

## 6. 网络设备：分清“控制谁”和“音频在哪里”

网络输出另设 `RemoteRenderer`，管理发现、能力、队列、状态与命令；不要把它塞进本地 `AudioOutput`，因为解码与时钟通常在远端。信号路径必须显示“手机/电脑仅控制，音频由网络设备拉取”或“本机转发音频”。设备广告支持某协议并不保证某个具体文件/码率可播。

| --- | --- | --- |
| DLNA/UPnP AV 与 OpenHome | Control Point / Sender | 第一批网络输出。发现、`ConnectionManager` 能力、AVTransport/RenderingControl 状态与音量、队列、seek、事件订阅；音量按 SCPD 公布的设备刻度显示，设置后必须 `GetVolume` 回读；未公布最大值时只读原始值并提供单步调整，不假设 0–100 百分比。OpenHome 播放列表可改善设备端队列及 gapless。设备差异要有兼容性测试。[UPnP renderer](https://upnp.org/specs/av/UPnP-av-MediaRenderer-v1-Device.pdf)、[RenderingControl v3](https://www.upnp.org/specs/av/UPnP-av-RenderingControl-v3-Service.pdf)、[OpenHome](https://openhome.org/pages/develop/overview.html) |

## 7. 共享架构与界面

建议在 `shared` 放**语义模型**，平台实现留在各端：

```text
PlaybackSource  ->  Decoder  ->  DspGraph  ->  FormatNegotiator
                                                |
                                      local AudioOutput / RemoteRenderer
                                                |
                                          SignalPathSnapshot
```

关键模型：

- `PlaybackSource`：本地文件、NAS/SMB、在线流、缓存；携带 URI、访问权限、是否允许远端拉取、可 seek 与有效期。
- `AudioFormat`：编码（PCM/DSD/DoP）、采样率、通道布局、有效位、容器位、字节序；DSD 用倍率/位速率，不挪用 PCM 的 kHz 字段。
- `OutputCapabilities`：设备 ID、后端、支持的候选格式、音量控制类型、独占/DSD 能力；来源为探测还是实测缓存。
- `PlaybackPolicy`：直通优先/必须直通/兼容优先、DSD 输出偏好、回退方式、缓冲大小、音量策略。
- `SignalPathSnapshot`：源 → 解码 → DSP → 转换 → 输出 → 设备的逐段状态，以及 `bitPerfectVerified` 与“不成立原因”。发布 UI 时“协商成功”与“数字采集验证”要分别用词。

界面遵循仓库 `AGENT.md` 的安静、自然语言原则：常规播放页只显示所选设备与简短状态（例如“USB DAC · 96 kHz · 直通”）；点开“音频路径”才显示全部格式和处理环节。设备选择器显示可用/占用/不支持原因。EQ 旁路一键可达。高级选项不干扰普通用户。播放器不得为了显示“HiFi”标识而隐藏回退或转换。

### Android P0 信号路径状态（代码已接入，实机验证未完成）

Android 设置页现在分开展示应用 DSP 状态、HAL mixer 偏好结果与源到输出链路评估。默认 limiter 开启时，即使 EQ 关闭，Android PCM 输出仍会经过 limiter，并可能执行整数 PCM dither；因此当前状态是 DSP 处理，而不是 bit-perfect 候选。只有 EQ 和 limiter 均旁路、AudioTrack 请求格式与实际格式一致、HAL 报告精确格式及 bit-perfect mixer 行为且接受偏好时，输出侧才通过候选检查。由于 Media3 renderer 输入不一定是解码后的 PCM，且当前没有 DAC 数字回采，源无损性、解码器样本保持和 DAC 实际输入仍属未知；界面不会把 HAL 接受或格式协商成功称为 bit-perfect。相关判定有 Android 单元测试覆盖，但仍需实机检查动态 EQ 状态刷新、Android 版本差异及 USB DAC 路由。

2026-10-05 Android PCM 测试音的临时 bit-perfect mixer preference 现先读取并保存旧值，读取失败时不写系统偏好；停止或 USB 路由失败时，只在当前值仍与本播放器写入值一致时恢复。系统读取/恢复失败会重试一次并记录日志，已被其他组件修改的值会保留。恢复策略由 JVM 单测覆盖；系统 AudioManager 行为与设备拔插仍待 Android 实机验证。

2026-10-05 Android 设置页新增可滚动的自定义 EQ 编辑器，可调前级与 10 个频段，支持旁路、limiter 与重置；拖动时实时预听，松手或关闭时保存，不逐帧写偏好。Android 与桌面选择预设都会启用 EQ。共享状态逻辑和 Android 构建已验证；矮屏/横屏布局及真实设备音频仍需实机验证。
